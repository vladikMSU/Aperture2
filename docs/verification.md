# Техническая проверка первой версии

Дата: 14 октября 2026. Среда: Windows, настольный Excel Microsoft 365 x64, VS 2022 Community / .NET Framework 4.8, Node 24.18, Python 3.12. Проверены интеграция и реальный запрос через OpenRouter/free; пользовательская приёмка финансового аудита остаётся отдельным этапом.

## Сборка и тесты

- Закреплённый Pi собран из исходников; установленные Python-зависимости проходят `pip check`.
- `scripts/build.ps1`: Runtime, Excel VSTO с подписанными manifests, PiSmoke — успешно.
- `scripts/test.ps1`: 8 backend-тестов, 5 проверок протокола/жизненного цикла Pi и 111 assertions панели — успешно. Регрессионные проверки панели описаны ниже.
- `git diff --check` — без ошибок пробелов.

Тесты панели компилируют настоящий `ChatPaneControl.cs` с тестовым представлением. Проверяют Stop и Dispose во время незавершённого старта, невозможность параллельного Send при Rebind/«Новый чат», ошибки запуска/отправки/остановки и фоновые RPC-события. Они не подменяют live smoke.

## Исправление UI и WebView2

Ошибка `InvalidOperationException` при обращении к `RichTextBox.TextLength` воспроизведена на прежнем контроллере: после `await PiSession.StartAsync` код продолжался в фоновом потоке, потому что Excel не предоставлял WinForms `SynchronizationContext`. Прежний harness устанавливал его сам и скрывал проблему. Новые сценарии отключают `WindowsFormsSynchronizationContext.AutoInstall`, очищают текущий контекст, создают настоящие HWND и включают `CheckForIllegalCrossThreadCalls`. Исправленный контроллер явно диспетчеризует UI и COM через `OnUiAsync`; отправка RPC инициируется до следующей команды Stop, ожидание остаётся асинхронным.

Основной чат заменён на WebView2 с локальными HTML/CSS/JS. Проверены начальный экран и диалог при ширине 410 и 320 px, таблица Markdown, потоковый текст, Send/Stop, настройки, disabled-состояния и вывод HTML из ответа как текста. Браузерная проверка `tests/web/chat-view.cjs`: 78 assertions, без ошибок JavaScript, внешних запросов и горизонтального переполнения. Скриншоты находятся в `work/chat-webview-*.png` (локально); текст аудита на демонстрационном скриншоте синтетический.

В настоящем Excel обе WebView2-панели сообщили `viewReady=true`, `viewInitializationError=null`; эти поля проверяются live harness после загрузки DOM и переключения книг. Это подтверждает загрузку встроенного WebView2, но не пользовательскую оценку удобства. Настройки остаются нативным WinForms-диалогом.

## Потоковый Markdown и ход работы

Предыдущий интерфейс форматировал Markdown только на `assistant_end`; в потоке показывал сырой текст. Контроллер также пропускал `thinking_*`, промежуточные результаты инструментов и нормальное завершение каждого вызова. Это объясняло неполный ход работы даже при исправном RPC. В диагностированной пользовательской сессии метаданные истории подтвердили два сообщения модели и один вызов `excel_target`, а не пропущенную серию чтений диапазонов. Блоки reasoning присутствовали, но были скрыты панелью. Содержимое пользовательской книги и reasoning в репозиторий не копировались.

Новая версия передаёт реальные события в WebView2, сопоставляет вызовы по `toolCallId`, показывает полученные reasoning-блоки и раскрываемые аргументы/результаты. Отрисовка Markdown обновляется с ограниченной частотой во время стрима; финальный текст сверяется с authoritative `message_end`. Шапка занимает 77 px при ширине 320/410/760 px; тест проверяет сохранение позиции прокрутки при чтении предыдущего текста. Проверены таблица, выделение и незакрытый блок кода до `assistant_end`, несколько инструментов с обратным порядком завершения, ошибки, отмена и финальное сообщение без дельт. Большие результаты инструментов рендерятся после раскрытия с явным пределом предпросмотра в 40 000 символов.

По уточнению пользователя список вызовов развёрнут по умолчанию; свёрнуты только подробности. Включены события `toolcall_start/delta/end`: формирование вызова видно ещё до `tool_execution_start`. Карточки сопоставляются по ID через обе стадии, поэтому повторные вызовы одного имени не сливаются, а один вызов не дублируется. Неизвестные интерфейсу имена также показываются; финальные tool-call блоки восстанавливают карточки, если событий формирования не было.

При отмене вызов, который ещё не начал исполняться, помечается «Не исполнен». Для начатой операции без завершающего события показывается «Нет результата»: остановка Pi не доказывает остановку COM-вызова или откат.

Для новых сессий уточнена инструкция модели: `excel_target` даёт только метаданные; зависимости требуют чтения формул. Это ограничение промпта, а не автоматическая гарантия качества. Модель не принуждается к фиксированному числу инструментов и второй агентный цикл не добавлен. Model smoke теперь сохраняет счётчики полученных событий без их содержимого, чтобы различать наличие стрима и завершённый ответ.

Повторный API-прогон после этих изменений: `.local/smoke/b5b5794340c24e0d82c75731aedf3697/report.json`. VSTO/WebView2 загрузились, прямой MCP read/write/calculate/readback прошёл. Pi прислал три `turn_start`, два успешных вызова инструментов, 2364 `thinking_delta` и 21 `text_delta`. Реальное чтение через модель вернуло 42 и `=SUM(A1:A2)`. Однако финальный ответ модели оказался `{"comB1":42.0,"formB1":""}` вместо запрошенного JSON: проверка корректности ответа **провалена**, exit code 1. Дальнейшие проверки после этого assertion, включая сравнение книги после модели, этим прогоном не подтверждены.

В истории этого теста `responseModel` менялся между шагами: `poolside/laguna-s-2.1:free`, `liquid/lfm-2.5-2.6b:free`, `nvidia/nemotron-3.5-lightning:free`. Это наблюдение конкретного запуска бесплатного маршрутизатора, а не оценка всех этих моделей. Дочерний Pi завершился; тестовый Excel очищен по тому же правилу точного handle, что описано ниже. Авторизацию и выбор модели пользователя не меняли.

Предыдущий прогон `.local/smoke/313517d6521545dfab1ddfb1451dcf57/report.json` также прошёл; тогда сверены хеши исходных HTML-ресурсов и файлов Debug-сборки.

## Проверка после Visual Studio Rebuild

По сообщению об исчезнувшей вкладке проверена сборка Visual Studio от 18:48: регистрация присутствовала, `LoadBehavior=3`, подпись и Inclusion List согласованы, хеши 14 файлов manifests совпадали. Свидетельств Office hard-disable и свежей ошибки загрузки не найдено. Чистый обычный запуск Excel автоматически загрузил эту сборку и WebView2: `.local/load-diagnostics/6b09300e2cd5478083b94da9d0baddaf/report.json`. Этот минимальный экземпляр завершился штатно.

Обычный MSBuild solution Rebuild воспроизвёл `MSB3061`: прежний фоновый Excel удерживал `bin/Debug/runtimes/win-x64/native/WebView2Loader.dll`. Пользователь завершил этот процесс; повторный Rebuild прошёл без предупреждения, последующий live smoke подтвердил автозагрузку. Причина исходного исчезновения вкладки отдельно не воспроизведена: блокировка DLL объясняет предупреждение сборки, но не доказывает отказ загрузки. Локальные настройки подписи Visual Studio и общие настройки доверия Office не изменялись.

В live harness убраны `COMAddIns.Update()` и принудительное `Connect=true`: теперь `vstoStartup.connectedAutomatically` проверяет фактический запуск, а отсутствие регистрации или подключения приводит к ошибке. Это закрывает пробел прежней проверки, которая могла самостоятельно восстановить подключение и скрыть проблему автозагрузки.

## Границы подтверждённого результата

В этом прогоне после `Quit` и освобождения внешних COM-ссылок пустой тестовый Excel оставался фоновым процессом. Harness завершил именно созданный им процесс по сохранённому handle после подтверждения нуля книг и отсутствия видимых окон. Отчёт явно содержит `normalExit=false`, `forcedTermination=true`; штатный выход процесса этим прогоном не доказан. Это поведение тестовой очистки, оно не добавлено в продукт: Aperture2 не завершает процесс Excel.

Два последующих минимальных запуска обычного Excel завершились штатно (`normalExit=true`, `forcedTermination=false`): с загруженной VSTO и с отключённой через `Connect=false` надстройкой. Оба выполнялись без обращения к диагностическому `COMAddIns.Object` и без MCP-нагрузки. Поэтому минимальный путь загрузки/выгрузки надстройки проверен, а причина удержания процесса в полном COM smoke отдельно не установлена. `Connect=false` также изменил сохранённый Office `LoadBehavior`; после диагностики developer-регистрация восстановлена. Локальный отчёт: `.local/smoke/lifecycle-isolation-c647f5ccc10045b3a117ac74f63b5988/report.json`.

Проверен один небольшой read-only сценарий модели. Качество финансового аудита, работа на больших моделях, пользовательское удобство и все сочетания сторонних надстроек не проверены. Браузерные команды/контроллер, загрузка VSTO/WebView2 и вызовы модели проверялись соответствующими отдельными harness; полный ручной сценарий ввода в панели остаётся пользовательской приёмкой. Авторизация выполняется через Pi. Для пользовательских книг нет автоматического сохранения, удаления, закрытия или обещанного отката.

## Сборка через Visual Studio без скриптов (14 октября 2026, вечер)

Скрипты `setup.ps1`, `build.ps1`, `unregister-dev.ps1`, `test-vsto.ps1` и `pi.ps1` удалены; упоминания их результатов выше относятся к прежней схеме. Причина прежних проблем с Rebuild: закоммиченный csproj выключал подпись, поэтому prebuild-шаг Visual Studio (`EnableClickOnceManifestsSigning` в `Microsoft.VisualStudio.Tools.Applications.Project.dll`) создавал `Aperture.Excel_TemporaryKey.pfx`, импортировал свой сертификат и переписывал csproj, а `build.ps1` подписывал другим сертификатом. По IL этого метода временный ключ создаётся только при пустом `ManifestCertificateThumbprint`; теперь там постоянная метка, а `build/Aperture.Signing.targets` подставляет отпечаток `CN=Aperture2 Development` до `ResolveKeySource` и подписи.

Проверено в чистом worktree:

- `msbuild Aperture2.sln /restore`: получение submodules, `npm ci` + сборка Pi, создание `.venv` и `pip check`, подпись и регистрация — успешно за 4 мин 9 с; повторная сборка пропускает зависимости по меткам `.local/deps` и занимает около 3 с, без предупреждений.
- `devenv.com Aperture2.sln /Rebuild` (IDE-путь с project flavor VSTO): 4 из 4 проектов, csproj не изменён, `*_TemporaryKey.pfx` и новые сертификаты не созданы; manifest подписан `CN=Aperture2 Development`. До метки этот же запуск воспроизводил генерацию временного ключа и правку csproj.
- `msbuild /t:Clean` снимает регистрацию надстройки и её inclusion entry; следующая сборка восстанавливает обе записи.
- `scripts/test.ps1`: 8 backend-тестов, 5 проверок runtime и 111 проверок панели (теперь проект `tests/vsto/PaneLifecycleHarness.csproj`) — успешно.
- Live smoke без модели `.local/smoke/ecfb790faf134aff98fc7b8b77f13434/report.json`: автозагрузка VSTO (`connectedAutomatically=true`), WebView2, MCP read/write/calculate/readback, Pi RPC и очистка панели — успешно; тестовый Excel, как и раньше, завершён по точному handle после `Quit`.

Попутно найдена ошибка запуска Pi: при кодовой странице консоли 65001 .NET Framework записывает в stdin дочернего процесса UTF-8 BOM раньше гейта `\n`, и `pi-launcher.mjs` завершался с «Aperture process gate failed». Runtime self-test падал так же и в основном checkout. Launcher теперь пропускает необязательный BOM; self-test проходит при консоли 65001 и 1251. В Excel без консоли это проявилось бы при системной кодовой странице UTF-8; на этой машине ACP = 1251.

## Скрытый Excel после закрытия (14 октября 2026)

Пользовательский Excel после работы с чатом и закрытия оставался скрытым процессом: в журнале надстройки `addin_shutdown` записан в 20:47:30, процесс без окон, книг и дочерних Pi/MCP продолжал работать; более ранний экземпляр висел не меньше 20 минут после выгрузки надстройки. Причина воспроизведена на одноразовых невидимых Excel (каждый завершён по собственному handle, пользовательские книги не участвовали):

| Сценарий | Завершение после `Quit` |
| --- | --- |
| Без MCP-клиента | за 2,5 с |
| `BoundSession` выполнила операцию, держит `_app`/`_workbook`, процесс убит (как Job Object) | не завершился за 45 с |
| То же, но ссылки освобождены до убийства | за 2,2 с |
| Исправленный `BoundSession` без ручного освобождения, процесс убит | за 2,2 с |

Теперь STA-воркер освобождает ссылки на Application/Workbook и кадры traceback исключений после каждой операции, до возврата результата, а книгу находит заново по имени, пути и HWND окна. Backend-тест проверяет отсутствие удерживаемых объектов после успеха и ошибки. Операция, убитая посреди COM-вызова, по-прежнему может оставить ссылку.

## Хронологическая лента чата (14 октября 2026)

По сообщению пользователя промежуточные ответы модели копились внизу, а вызовы инструментов и рассуждения — в одной карточке сверху; итоговый ответ отделялся строкой `---`. Причины: текст шёл отдельным каналом `assistant_delta` в отдельный пузырь, а activity — в карточку, созданную первым событием; Markdown-рендерер не знал горизонтальной линии. Теперь контроллер передаёт представлению все `message_update`, включая `text_*`, а `chat.js` строит одну ленту по `contentIndex`: текст, рассуждения и вызовы в порядке событий, подряд идущие шаги в компактной группе, итоговый ответ остаётся видимым при сворачивании хода работы. Рендерер поддерживает `---`, курсив, цитаты, вложенные списки и выравнивание столбцов; HTML и ссылки из ответа остаются текстом. Тема панели следует явной теме Office, иначе теме Windows.

- `tests/web/chat-view.cjs`: 99 проверок в headless Edge, включая порядок элементов ленты, `---` как разделитель и сворачивание без потери ответа; без ошибок JavaScript и внешних запросов. Скриншоты тёмной/светлой темы и ширины 320 px просмотрены.
- Тест панели: 112 проверок; backend: 9 тестов; runtime self-test: 5 проверок.
- Live smoke без модели `.local/smoke/c8671fef1b904fc2ab224a6aa4181227/report.json`: автозагрузка VSTO, обе WebView2-панели `viewReady=true` без ошибки инициализации, MCP read/write/calculate/readback, Pi RPC. Тестовый Excel после `Quit` впервые завершился штатно (`normalExit=true`, `forcedTermination=false`) — эффект освобождения COM-ссылок MCP.

Визуальное удобство в настоящей панели Excel и поведение на длинном реальном аудите с моделью остаются пользовательской приёмкой.
