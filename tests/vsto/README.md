# Проверка жизненного цикла панели

`PaneLifecycleHarness.csproj` входит в `Aperture2.sln` (папка `tests`) и собирается вместе с решением. Запуск: в Visual Studio **Debug → Start Without Debugging** на этом проекте или `tests\vsto\bin\Debug\net48\PaneLifecycleHarness.exe`; `scripts\test.ps1` запускает его вместе с остальными проверками. Код возврата 0 означает успех.

Проект компилирует настоящий `src/Aperture.Excel/ChatPaneControl.cs` вместе с явно тестовыми зависимостями из `FakeDependencies.cs`. Он запускает скрытые WinForms-контролы с созданными HWND и STA message loop; `ChatPaneView` заменяется fake с проверкой потока каждого вызова. Excel, WebView2, Pi, COM и модель не запускаются. Ключи и локальные настройки пользователя не читаются.

163 проверки начинаются с 11 базовых проверок жизненного цикла: Stop во время отложенного старта, конкурирующий Send во время «Нового чата» и закрытие панели во время старта. Тестовая фабрика намеренно возвращает процесс после отмены, проверяя, что панель освободит его и не отправит отложенный запрос.

Регрессия VSTO воспроизводится с `SynchronizationContext.Current = null` в момент вызова команды, `WindowsFormsSynchronizationContext.AutoInstall = false` и `Control.CheckForIllegalCrossThreadCalls = true`. Завершение запуска, ошибка, отмена, ответ RPC, остановка и события Pi поступают с рабочих потоков. Проверяется возврат изменений UI и проверки привязки книги в основной поток, сохранение занятого состояния при неизвестном результате после тайм-аута и его снятие после подтверждённой остановки. Инициация отправки prompt должна происходить в UI-блоке перед последующей командой Stop; само ожидание ответа остаётся асинхронным.

Проверки activity передают реальные формы событий из закреплённого Pi: `thinking_*`, итоговый `message_end`, несколько инструментов с `toolCallId`, промежуточный результат и завершение в другом порядке. Подтверждаются передача reasoning без дублирования текстовых дельт, восстановление полного финального ответа, завершение карточек после Stop/ошибки, сохранение ошибки провайдера при `agent_settled` и успешное восстановление после автоматического повтора. Событие старой сессии, захваченное до отписки, не должно попадать в новый чат; ошибка до отправки не переписывает предыдущую завершённую activity, а «Новый чат» заново привязывает книгу окна, если чат её потерял.

Строки статуса нет, поэтому fake-представление записывает уведомления ленты. Проверяется, что ошибки запуска, отказа и привязки до отправки идут отдельной строкой, а ошибка ответа, неизвестный итог после тайм-аута, неподтверждённая остановка, принудительное завершение Pi и завершение агента во время запроса — в карточку запроса. Ход работы, инструменты и повторы провайдера уведомлений не создают; stderr Pi не показывается построчно, но последняя строка поясняет завершение агента.

Смена имени книги (fake «первое сохранение / Save As»): следующий запрос останавливает прежний Pi, продолжает тот же файл истории (`ResumeAsync`) с той же книгой и ID под новым именем, ничего не объявляет в ленте и не перезапускает Pi на следующих запросах. Неудачное продолжение повторяется следующим запросом, «Новый чат» начинает заново. Если прежний Pi уже завершился, начинается новая сессия с системной строкой. `Start` на переименованной книге привязывает её заново в новом чате.

События формирования `toolcall_start`, `toolcall_delta` и `toolcall_end` передаются до исполнения вместе с именем, идентификатором, фрагментом аргументов и финальным `toolCall`. Контроллер не отбрасывает незнакомые имена и повторяющиеся идентификаторы: связывание карточек выполняет представление, полный `message_end` остаётся резервным источником.

Ответ prompt с `disposition: handled` завершает занятость только после `get_state.isStreaming = false`: команды расширений вроде `/mcp` не создают `agent_settled`. Ответы `started`, `queued` и `handled` при активном Pi сохраняют занятость. Эти проверки не оценивают HTML/CSS или визуальное представление карточек — интерфейс проверяется отдельно.

На прежнем контроллере тот же сценарий старта воспроизводил `InvalidOperationException` в `RichTextBox.get_TextLength` → `ChatPaneControl.AppendMessage` → `SendAsync`. Снимки исходного контроллера, harness и стек сохранены локально в игнорируемой `.local/tests/vsto`; проект всегда проверяет текущий `ChatPaneControl.cs`.

Запуск через COM-вход (`StartScripted`) проверяется на том же контроллере: синхронный захват чата и отказ второго запуска, новый чат с провайдером и моделью скрипта, сохранение черновика, путь истории Pi, состояния `done`, `failed` и `cancelled`, отказ при запросе в другом окне, сброс модели скрипта при «Новом чате». «Стоп» без ответа Pi через сокращённый бюджет завершает процесс этого чата и объясняет это в ленте. `Start` на панели, у которой ещё нет окна (только что созданной), принимает запрос сразу, а отправляет его, когда окно появилось; `Cancel` в это время даёт `cancelled` без запуска Pi, а панель, не открывшаяся за сокращённый срок, — `failed`.

Это регрессионные проверки панели, а не подтверждение живого управления Excel. Загрузка VSTO, кнопка на «Главной», создание панели по требованию, удаление панелей закрытых окон и работа MCP проверяются отдельным live smoke.
